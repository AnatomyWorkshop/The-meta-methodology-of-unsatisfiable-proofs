# MCP 接入计划

> 这份文档描述 Illusion 如何通过 MCP（Model Context Protocol）扩展 L2 的搜索空间。
> 状态：规划中。随实现迭代更新。
> 最后更新：2026-05-06（Phase 3 完成后，开始具体规划）

---

## 一、为什么需要 MCP

当前 L2 的搜索空间是手写的变换规则库。Phase 1 有 9 个变换，Phase 3 有 9 个。每个新领域都需要人工设计变换。这是当前最大的瓶颈——系统只能从人工预设的菜单里选，不能自己生成候选。

MCP 的目标：让 L2 能调用外部工具来**生成**和**验证**候选变换，而不是只从预定义列表里选。

核心约束不变：**任何 AI 生成的候选性质都必须通过 L3 的自指安全检查。** MCP 扩展的是 L2 的能力，不是绕过 L3。

---

## 二、三个接入方向（按优先级排序）

### 方向 1：自动变换生成（最高优先级）

**问题**：当 L2 搜索空间穷尽后，下一步靠人工添加变换。这是瓶颈。

**方案**：通过 MCP 让 AI 在发现 UNKNOWN 或搜索空间耗尽时，自动提议新的变换类。

**工作流**：
1. L2 搜索完成，所有候选要么被 L3 分类，要么搜索空间耗尽
2. MCP 调用 AI → 输入：当前领域描述（L1 模型类、目标函数、已有变换及其结果）
3. AI 输出：1-3 个新变换的描述（自然语言 + 伪代码）
4. 人类审查 AI 提议 → 确认后实现为 Python 代码
5. 新变换加入注册表 → L2 重新搜索

**L3 安全边界**：AI 生成的变换仍然必须通过 L3 检查。AI 不能绕过自指安全。

**实现复杂度**：中等。需要定义 MCP tool schema、prompt 模板、变换描述格式。

---

### 方向 2：文献检索辅助 L3（中等优先级）

**问题**：L3 的规则库是手写的。遇到 UNKNOWN 时，人类需要自己判断"这个性质是否在 L1 内可判定"。

**方案**：通过 MCP 让 AI 在遇到 UNKNOWN 时，自动检索相关文献，提供判定依据。

**工作流**：
1. L3 返回 UNKNOWN
2. MCP 调用 AI → 输入：变换名、描述、L1 模型类
3. AI 检索 arXiv / 教科书 / 已知结果 → 输出：该性质的已知可判定性结果
4. 人类参考 AI 检索结果做最终 L3 判定
5. 判定结果通过 UNKNOWN 学习循环持久化

**L3 安全边界**：AI 的检索结果是**辅助输入**，不是最终判定。人类仍然做 L3。

**实现复杂度**：低。主要是 prompt 工程，不需要改 L3 核心逻辑。

---

### 方向 3：实验自动化（低优先级，长期）

**问题**：每次切换领域（AC⁰ → 单调 → 代数），需要手动实现 L1 模拟器和变换库。

**方案**：通过 MCP 让 AI 根据领域描述自动生成 L1 模拟器和初始变换库的代码骨架。

**工作流**：
1. 人类指定新领域（"代数电路，目标函数 = 永久式"）
2. MCP 调用 AI → 输出：L1 模拟器骨架、分布采样器、3-5 个初始变换
3. 人类审查 + 修正 → 运行 L2 搜索
4. 迭代

**L3 安全边界**：AI 生成的代码由人类审查。L3 规则库需要人类为新领域手写初始规则。

**实现复杂度**：高。需要 AI 理解电路模型的形式化定义，生成正确的模拟器代码。

## 三、技术架构

```
┌─────────────────────────────────────────┐
│  Illusion Core                          │
│  ┌─────┐  ┌─────┐  ┌─────┐             │
│  │ L1  │  │ L2  │  │ L3  │             │
│  └──┬──┘  └──┬──┘  └──┬──┘             │
│     │        │        │                 │
│     │   ┌────┴────┐   │                 │
│     │   │ MCP Hub │   │                 │
│     │   └────┬────┘   │                 │
└─────│────────│────────│─────────────────┘
      │        │        │
      ▼        ▼        ▼
  [L1 模拟]  [变换生成]  [文献检索]
             [代码生成]  [可判定性查询]
```

MCP Hub 是 L2 和 L3 的扩展接口，不是替代。核心搜索循环不变。

## 五、不做什么

- 不让 AI 直接修改 L3 规则库（人类审查是硬约束）
- 不让 MCP 绕过 L3 安全检查
- 不追求"全自动"——人类在 L3 和方向决策上的角色不变
- 不在 MCP 接入前切换到新领域——先在已有领域（AC⁰ / 单调）上验证 MCP 流程

## 六、开放问题

1. **变换描述格式**：AI 生成的变换用什么格式描述？自然语言 + 伪代码？还是直接生成 Python 类？前者更安全（人类审查后再实现），后者更快。
2. **文献检索的可靠性**：AI 检索到的"已知结果"可能是幻觉。需要人类验证。是否需要要求 AI 给出具体引用（论文标题 + 定理编号）？
3. **MCP 协议版本**：使用哪个版本的 MCP spec？需要确认 Claude Code 当前支持的 MCP 能力。
4. **等价性标注**：当 MCP 接入 Lean/Coq 后，L3 需要判断 Lean 给出的等价性证明是否在 L1 内可判定。传统等号不携带这个信息。这个问题的设计留到遇到第一个具体案例时再展开（见 `note-equivalence-annotation.md`）。

## 七、更大的视野：MCP 之后 Illusion 能走多远

这一节是方向性设想，不是承诺。

### 7.1 代数电路（Phase 4 候选）

代数电路（加法/乘法门，无布尔约束）的下界证明使用代数方法（Razborov-Smolensky、Nisan-Wigderson）。目标函数候选：永久式（Permanent）。

这是 MCP 接入后最自然的第一个新领域：
- L1 替换为代数电路模拟器（有限域上的多项式计算）
- 目标函数：Permanent（已知需要指数规模代数电路，Valiant 1979）
- 变换库：代数限制（analogous to random restriction）、次数降低、单项式消除
- L3 新规则：代数次数是否在代数 P/poly 内可判定

如果 MCP 能帮助生成初始变换库，这个领域的接入成本会从"1 周手写"降到"2-3 天审查 + 修正"。

### 7.2 证明复杂度（更远的目标）

Resolution、Frege、Cutting Planes——这些证明系统的下界证明（如 Ben-Sasson-Wigderson 的宽度方法）有和电路下界完全不同的结构。

这里的等价性问题会变得核心：证明系统里的"等价"是语义等价（两个公式有相同的真值表）还是证明等价（两个公式有相同的最短证明）？这两种等价性的可判定性完全不同。这是 `note-equivalence-annotation.md` 里的符号标注问题第一次会变成实际工程问题的地方。

### 7.3 如果 MCP 接入 Lean 成功

最远的设想：Illusion 的 L2 通过 MCP 调用 Lean，把候选变换的"自指安全性"翻译成 Lean 里的一个可验证命题，然后 Lean 给出形式化证明或反例。

这不是"AI 证明定理"。这是"AI 把一个元数学判断（这个性质是否在 L1 内可判定）翻译成一个对象层面的数学命题，然后用形式化工具验证"。

如果这条路走通，L3 的 SAFE/UNSAFE 判定就不再只是规则匹配，而是有形式化证明支撑的判定。这会把 Illusion 从"实验性原型"变成"有形式化保证的搜索系统"。

这是 5 年的事，不是 5 个月的事。但它是这条路的终点形状。
